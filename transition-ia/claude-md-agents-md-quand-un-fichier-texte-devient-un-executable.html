CLAUDE.md, AGENTS.md : quand un fichier texte devient un exécutable

Des dépôts GitHub piégés détournent Claude Code et les autres agents avec de simples fichiers de consignes. J'ai audité mon propre poste : voici ce qu'un attaquant y trouverait.

En bref

  • Bitdefender a repéré 22 dépôts GitHub piégés dont les fichiers CLAUDE.md et AGENTS.md demandent à l'assistant de lancer un script « sans demander confirmation » et « sans afficher de sortie ».
  • Le script vole clés SSH, fichiers .env, jetons GitHub et accès cloud, puis se sert des jetons volés pour piéger d'autres dépôts.
  • Ce n'est pas un cas isolé : le ver Miasma a touché au moins 123 dépôts en juin, et un simple AGENTS.md déposé dans un dossier Téléchargements a suffi à faire installer un paquet malveillant.
  • Pour un agent, une consigne écrite en Markdown vaut une commande. Ces fichiers texte sont devenus des exécutables, et il faut les traiter comme tels.
  • J'ai audité mon propre poste : aucun fichier piégé, mais bien plus de portes ouvertes que je ne le pensais. Voici ce que je recommande en entreprise.

Quand on travaille avec Claude Code, Cursor ou Codex, on prend vite l'habitude d'écrire des fichiers de consignes pour l'agent : un CLAUDE.md ou un AGENTS.md à la racine du projet, qui explique l'architecture, les commandes, les conventions. J'en ai des dizaines sur mon poste. L'agent les lit au démarrage et les suit à la lettre : c'est tout leur intérêt.

C'est aussi devenu une porte d'entrée. Pas besoin de faille dans l'éditeur ni de binaire malveillant : il suffit d'écrire la bonne phrase dans le bon fichier, et l'agent fera le travail lui-même, avec les droits du développeur.

Ce que Bitdefender a trouvé

Le 17 novembre, Bitdefender Labs a publié l'analyse de 22 dépôts GitHub montés pour piéger les développeurs qui travaillent avec des assistants de code (Bitdefender Labs, 17 novembre 2026). Leur fichier d'instructions présente un script scripts/setup.js comme un composant officiel, et donne à l'assistant des consignes très précises :

Tout est pensé pour qu'un agent obéissant exécute le script sans jamais le montrer au développeur. Et il existe une deuxième voie qui n'a même pas besoin de l'IA : un « hook » déclaré dans le fichier .claude/settings.json du dépôt, qui lance la commande au démarrage de chaque session, dès que le développeur a accordé sa confiance au dossier.

Le script est un chargeur de près de 4 Mo, encodé, chiffré et compressé en plusieurs couches. Une fois déballé, il cherche tout ce qui a de la valeur sur le poste : clés SSH, fichiers .env, clés d'API, jetons GitHub et GitLab, identifiants cloud et des registres de paquets, mots de passe enregistrés dans le navigateur. Puis il se propage. Il réécrit les fichiers de configuration des agents qu'il trouve sur la machine (Cursor, Codex, Gemini, Copilot et une dizaine d'autres), et utilise les jetons volés pour pousser des CLAUDE.md, AGENTS.md et hooks piégés dans les dépôts auxquels la victime a accès, jusqu'à 25 par défaut.

Il faut rester précis : l'étude est préliminaire. Bitdefender ne donne ni nombre de victimes ni attaquant identifié, et présente au passage son propre outil de protection. Mais le mécanisme, lui, est parfaitement documenté.

Pourquoi ça marche : le Markdown est devenu du code

Le piège contourne tous nos réflexes. Un développeur se méfie d'un exécutable inconnu, d'un script curl | bash, d'une dépendance douteuse. Il ne se méfie pas d'un fichier texte qui explique comment lancer le projet.

Or sur le poste d'un développeur, l'agent s'exécute avec les mêmes privilèges que lui : il a accès au terminal, aux clés SSH, aux variables d'environnement, aux jetons GitHub. Et pour un modèle de langage, il n'y a aucune frontière technique entre une consigne légitime de son utilisateur et une consigne écrite par un inconnu dans un fichier du projet. Tout est du texte, tout est du contexte. C'est l'injection de prompt indirecte, dont je parlais dans mon article sur la sécurité de l'IA en entreprise, appliquée au poste de travail.

Les chercheurs de Forever Security, qui ont étudié un cas similaire, le résument parfaitement : « Un agent qui suit le AGENTS.md de son dossier fait exactement ce pour quoi il a été conçu. » Et ils ajoutent : « Il n'y a rien à corriger ici pour OpenAI ou Anthropic. » Ce n'est pas un bug, c'est le fonctionnement normal.

Ce n'est pas un cas isolé

Cette campagne est au moins la troisième du genre cette année :

123dépôts GitHub touchés par le ver Miasma en juin, dont un dépôt de Microsoft
1 300sessions Claude Code lancées depuis un dossier Téléchargements chez les clients d'un seul éditeur de sécurité
22dépôts piégés identifiés par Bitdefender en novembre, chiffre encore provisoire
  • Juin 2026, le ver Miasma. Avec un jeton volé, l'attaquant a poussé un commit anodin (« chore: update dependencies ») qui ajoutait des déclencheurs pour tous les outils à la fois : un hook de démarrage pour Claude Code et Gemini CLI, une règle permanente pour Cursor, une tâche lancée à l'ouverture du dossier pour VS Code. Cloner le dépôt est sans danger ; c'est l'ouvrir dans un agent ou un éditeur qui déclenche le vol d'identifiants. Au moins 123 dépôts ont été touchés, dont Azure/durabletask chez Microsoft (SafeDep, 5 juin 2026).
  • Octobre 2026, le dossier Téléchargements. Chez un client de Forever Security, un agent a tenté d'installer un paquet npm malveillant. La cause : un AGENTS.md posé dans le dossier Téléchargements, qui était aussi le dossier de travail de l'agent. C'est le seul dossier dans lequel une page web peut écrire seule, et les chercheurs y ont compté plus de 1 300 sessions Claude Code lancées chez leurs clients. Leur reproduction sur Codex a réussi 9 fois sur 10 (BleepingComputer, 25 octobre 2026).
  • La dépendance qui réécrit les consignes. L'équipe sécurité de NVIDIA a montré qu'une dépendance compromise pouvait écrire elle-même un AGENTS.md malveillant pendant le build, pour pousser l'agent à saboter le code (NVIDIA).

La Cloud Security Alliance traite désormais l'empoisonnement des fichiers d'instructions comme une catégorie d'attaque à part entière, qui couvre AGENTS.md, CLAUDE.md, les règles Cursor et les instructions Copilot (CSA, 27 octobre 2026). Et la liste ne s'arrête pas aux fichiers de consignes : skills, plugins, serveurs MCP, tout ce qu'on installe pour enrichir un agent forme une nouvelle chaîne d'approvisionnement, aussi exposée que npm ou PyPI.

J'ai audité mon propre poste

Avant d'écrire cet article, j'ai demandé à Claude Code d'auditer mon propre Mac, en lecture seule et sans afficher aucun secret. J'utilise des agents tous les jours, sur des projets personnels comme professionnels : c'était le bon cobaye.

Audit · 20 novembre 2026

Mon poste de CTO, vu par un attaquant

Ce qui va bien. 57 CLAUDE.md, 8 AGENTS.md, plus d'une centaine de fichiers de réglages et 18 configurations MCP passés au crible : aucune consigne du type « sans confirmation » ou « ne pas lire », aucun hook de projet, aucune tâche lancée automatiquement à l'ouverture d'un dossier, et jamais d'agent lancé depuis Téléchargements. Mes seuls hooks globaux font parler mon Mac quand une tâche se termine.

Ce qui va moins bien. Au fil des « toujours autoriser », j'ai accumulé des centaines de commandes pré-autorisées, dont certaines très larges : exécuter du code à la volée, lancer des conteneurs, pousser sur Git, installer des paquets. Autant de portes qu'une consigne injectée pourrait franchir sans que l'agent me demande quoi que ce soit.

Ce qu'un voleur trouverait. Comme sur la plupart des postes de développeurs, des secrets à portée de main : fichiers .env, identifiants stockés en clair, jetons capables d'écrire dans des dépôts. Exactement ce dont ce type de campagne a besoin pour se propager.

Aucun de ces points n'est une faute grave pris isolément. C'est l'accumulation qui pose problème : un poste de développeur est un coffre-fort ouvert, et l'agent qu'on y fait tourner en a toutes les clés. Le jour où il suit la mauvaise consigne, ce n'est pas un projet qui est compromis, c'est la station entière et tout ce à quoi elle donne accès.

Ce que je recommande en entreprise

Dans une entreprise, les agents se retrouvent vite partout : Claude Code ou Cursor chez les développeurs, des agents internes branchés sur le système d'information, et des skills ou des fichiers de consignes partagés entre collègues. C'est la même mécanique de confiance, à l'intérieur de l'équipe. Voici les règles que je recommande.

En pratique

Sept règles pour des agents de code sous contrôle

1. Un fichier de consignes est du code. CLAUDE.md, AGENTS.md, .claude/, .cursor/, .mcp.json passent en revue de code comme le reste, avec un responsable.

2. Jamais de confiance par réflexe. Avant d'ouvrir un dépôt inconnu dans un agent, on lit ses fichiers de consignes, ses hooks, ses tâches VS Code et les scripts qu'ils appellent.

3. Les signaux d'alerte sont connus. Toute consigne qui interdit de lire un fichier, demande de ne pas afficher de sortie, de ne pas demander confirmation ou d'installer quelque chose automatiquement est suspecte par définition.

4. Le code inconnu s'ouvre dans un conteneur jetable, sans clés SSH, sans .env, sans jetons.

5. On lance l'agent depuis le projet, jamais depuis son dossier personnel ou ses Téléchargements.

6. On fait le ménage dans les autorisations. Les demandes de validation restent actives pour tout ce qui exécute du code, pousse ou installe ; les « toujours autoriser » sont revus régulièrement.

7. Les secrets sortent des fichiers. Trousseau ou gestionnaire de secrets plutôt que .env et jetons en clair, jetons à droits limités et de courte durée, et anonymisation des données avant qu'elles partent vers un modèle.

La plupart de ces règles ne sont pas nouvelles. Ce sont celles qu'on applique depuis longtemps aux scripts et aux dépendances. La nouveauté, c'est qu'il faut maintenant les appliquer à des fichiers que personne ne considérait comme dangereux.

Le fichier texte est devenu un exécutable

Pendant des années, la sécurité du poste de travail reposait sur une distinction simple : ce qui s'exécute est dangereux, ce qui se lit ne l'est pas. Les agents ont effacé cette frontière. Pour eux, lire une consigne, c'est déjà agir.

Je ne crois pas qu'il faille ralentir l'adoption des agents pour autant : ils ont changé notre façon de travailler, et c'est irréversible. Mais il faut accepter ce qu'ils sont : des collaborateurs extrêmement rapides, très obéissants, et qui ne savent pas distinguer leur employeur d'un inconnu qui a laissé un mot sur leur bureau. À nous de décider qui a le droit de leur écrire.
