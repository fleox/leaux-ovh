Transition IA

Piloter un agent IA interne (Hermes) avec des Skills Python plutôt que des MCP

Une trentaine de skills, une dizaine de MCP, et un agent qui hésite : comment on a tout restructuré autour d'un router, de petits skills spécialisés et de Skills Python maison.

Frédéric Leaux8 septembre 202615 min de lecture

Voici l'erreur que beaucoup d'équipes font en déployant un agent IA interne à l'échelle d'une entreprise.

On démarre petit : quelques MCP branchés, deux ou trois skills maison, tout fonctionne. Alors on ajoute au fil de la demande. Une trentaine de skills et une dizaine de MCP plus tard, l'agent hésite, charge les mauvais outils, ralentit.

L'erreur pour nous n'était pas d'avoir trop de capacités — c'était de ne pas avoir pensé l'architecture au moment de passer de « quelques skills » à « beaucoup de skills ». Un seuil traître, sans warning.

On a fini par tout restructurer autour d'un pattern précis : un router qui aiguille, des skills spécialisés petits, une discipline stricte sur les descriptions frontmatter, et des Skills Python maison à la place des MCP tiers.

Résultat : plus d'hésitation, le bon outil du premier coup, et on peut continuer d'ajouter des capacités sans dégrader ce niveau.

Comment fonctionne l'agent Hermes

Hermes est l'agent IA qu'on pilote en interne. Comprendre comment il découvre et charge les skills n'est pas un détail d'implémentation : c'est ce qui conditionne toute son efficacité. Sans cette compréhension, on choisit mal ses outils, on découpe mal ses skills, et l'agent devient lent et confus.

Et c'est de plus en plus vrai à mesure qu'on ajoute des fonctionnalités. Avec 3 skills et 2 MCP, tout marche à peu près sans y réfléchir. Avec 30 skills et une dizaine de MCP branchés, le moindre écart se paie cash : ambiguïtés de routage, contexte qui gonfle, réponses qui ralentissent.

Au démarrage d'une conversation, Hermes scanne son répertoire de skills et lit le frontmatter YAML de chaque SKILL.md. Il en construit un manifest minimal : juste le nom et la description de chaque skill. Rien d'autre.

Exemple de frontmatter YAML dans un SKILL.md :

---
name: nsn-elasticsearch
description: "Elasticsearch read-only (logs.n10.xyz) — logs d'accès WordPress pour TOUS les sites NSN dans un seul stream. À utiliser pour 'logs du site X', 'combien d'erreurs 500 sur Y aujourd'hui', 'dernières requêtes sur Z', 'top URIs par trafic'. Les sites sont identifiés par le namespace k8s (sites dynamiques) ou labels.app (sites statiques) — le flag --site résout les deux automatiquement."
version: 1.0.0
platforms: [macos, linux]
metadata:
  hermes:
    tags: [nsn, elasticsearch, logs, kibana, elk, wordpress, nginx, observability]
    category: nsn-ops
prerequisites:
  commands: [python3]
---

... Instructions du skill ...

À chaque message utilisateur, le LLM voit le message, plus la liste des couples (nom, description) de tous les skills disponibles.

Il choisit un skill quand la description matche sémantiquement l'intention. Il émet alors une invocation interne, Hermes lit le SKILL.md complet et l'injecte dans le contexte pour le tour suivant. Le corps contient la CLI, les exemples, les pièges. Le LLM exécute ensuite le script Python associé via un outil terminal.

Schéma du flux : « quels sont les meilleurs buteurs de la Ligue 1 ? »

Le principe clef : la progressive disclosure. Seul le frontmatter est chargé en permanence. Le corps du SKILL.md, souvent 100 à 300 lignes de doc, CLI et exemples, n'arrive dans le contexte que quand le LLM choisit ce skill précis.

Concrètement : une description bien écrite coûte 30 à 60 tokens. 100 skills, c'est donc 3 000 à 6 000 tokens de manifest permanent. Non négligeable, mais sans commune mesure avec les 30 000 et plus qu'on aurait en chargeant tous les corps. C'est ce mécanisme qui rend le découpage fin viable.

Le pattern Router + Specialists

Le découpage qu'on a fini par adopter :

  • Une catégorie = un domaine métier (données produit, ops, monitoring, utilitaires).
  • Dans chaque catégorie, un skill « router » dont le seul but est d'aiguiller.
  • Autour du router, N skills spécialisés (typiquement 3 à 10), chacun couvrant un sous-domaine de questions.

Analogie : la réception d'une entreprise. Un standard qui écoute la demande, comprend ce que veut la personne, et transfère au bon bureau. Chaque bureau est petit, ne fait qu'une chose, la fait bien.

config/skills/<category>/
├── DESCRIPTION.md            ← description de la catégorie
│
├── <category>-overview/      ← LE ROUTER
│   ├── SKILL.md              → description parapluie + table de décision
│   └── scripts/
│       ├── api_client.py     → client HTTP partagé (stdlib only)
│       └── config.py         → URLs + tokens
│
├── <category>-<domaine-A>/   ← skill spécialisé
├── <category>-<domaine-B>/
└── <category>-<domaine-C>/

Le router a une description volontairement large qui liste tous les mots-clés du domaine et se termine par « Load this FIRST when the user asks anything about <domaine> ». Le LLM le charge quasi systématiquement dès qu'une question du domaine arrive.

exemple de Skill ROUTER :

---
name: sports-overview
description: "Routeur + client API partagé pour toutes les questions sports/cotes (fixtures, live, cotes, stats d'équipes, value bets, arbitrage). À charger EN PREMIER dès que le user pose une question liée au sport — il pointe vers le bon skill spécialisé et héberge le client HTTP SportMonks + Odds-API partagé entre chaque script sports-*."
version: 1.0.0
author: Hermes Sports Expert
license: MIT
platforms: [macos, linux]
metadata:
  hermes:
    tags: [sports, football, tennis, basketball, betting, odds, live, fixtures, router]
    category: sports
    related_skills:
      - sports-fixtures
      - sports-live
      - sports-odds
      - sports-team
      - sports-standings
      - sports-player
      - sports-transfers
      - sports-coach
      - sports-injuries
      - sports-referee
      - sports-insights
      - sports-search
      - sports-meta
    config:
      - key: ...
      - key: ...
        prompt: Clé API ...
prerequisites:
  commands: [python3]
---

# Sports & Cotes de betting — Routeur

Tu es un **expert sportif**. Toute question qui touche à des matchs,
scores, cotes, équipes, championnats, bookmakers, paris ou prédictions
est dans ton périmètre. Tu as un accès direct à deux APIs via le
client Python partagé de ce skill ; aucun backend externe n'est requis.

...

Une fois chargé, le corps du router contient une table de décision qui associe une intention utilisateur à un skill :

  • « matchs du jour », « programme du week-end » → /sports-fixtures
  • « score live », « match en direct » → /sports-live
  • « cotes du match X », « meilleure cote » → /sports-odds
  • « stats de X », « meilleurs buteurs » → /sports-player
  • « classement Ligue 1 » → /sports-standings

Le LLM lit la table, choisit un ou plusieurs skills spécialisés, et enchaîne. Une question composée (« cotes des matchs du jour en Ligue 1 ») charge deux skills en séquence.

Chaque skill spécialisé a une description étroite, avec des exemples de phrasings concrets et des clauses « NOT for X, see /other-skill ».

Point important : rien ne dit à l'agent « ce skill est le router ». Aucun flag, aucune convention magique. Le pattern repose sur trois leviers de contenu, tous dans le SKILL.md du router :

  1. Description parapluie dans le frontmatter, qui matche tous les mots-clés du domaine.
  2. Instruction en langage naturel : « Load this FIRST when the user asks anything about X ».
  3. Table de décision dans le body, visible une fois le router chargé.

Le pattern émerge de la discipline sur les descriptions, pas d'un mécanisme du framework.

Pourquoi ce pattern plutôt que des MCP ?

Précisons d'abord de quels MCP on parle, parce que l'arbitrage n'est pas le même partout. Le protocole supporte plusieurs transports : des serveurs locaux en stdio (souvent Node lancés via npx, parfois Python ou un binaire) et des serveurs distants en HTTP. Notre critique porte sur les serveurs stdio tiers, ceux qu'on lance dans nos pods. Un MCP distant maintenu par un éditeur, avec un contrat d'API stable, c'est un autre débat.

Sur le papier, c'est séduisant : à peu près tout outil du marché a déjà un MCP officiel ou communautaire. Dans les faits, six problèmes concrets nous ont fait basculer.

1. Chaîne de démarrage

npx va chercher le paquet au registre à la première utilisation, puis spawne un process Node. En pratique le serveur démarre à l'initialisation de la session, pas à chaque appel d'outil. Mais ça reste, pour chaque MCP branché, une dépendance réseau au démarrage et un process de plus à surveiller dans le pod.

Un skill Python maison, c'est un python3 script.py lancé par l'outil terminal : un process court, quelques dizaines de millisecondes de démarrage d'interpréteur, aucune dépendance au registre npm en production. Ce n'est pas « zéro coût », c'est un coût qu'on maîtrise et qui ne dépend de personne.

Contrepartie honnête : un skill coûte un tour de LLM de plus qu'un MCP — charger le SKILL.md, puis lancer la commande — là où un tool MCP est appelable directement. Sur une question simple, un MCP bien nommé peut être plus court en latence de bout en bout. Le gain se fait sur la fiabilité du routage quand le nombre d'outils grimpe, pas sur l'appel unitaire.

2. Maîtrise : c'est ton code, dans ton repo

Un MCP tiers, c'est du code que tu n'as pas écrit, qui change à chaque version, avec des dépendances qui suivent leur propre calendrier. Ta CI ne le teste pas. Tes revues de code ne le voient pas. Un jour l'upstream ajoute une « feature » qui change le comportement, tu le découvres en prod.

Un skill Python maison, c'est 100 à 300 lignes qui vivent dans ton repo. Tu les revois, tu les testes, tu les audites. Un bug de comportement, tu l'ouvres dans ton IDE et tu le corriges en 5 minutes.

3. Sécurité : le refus est dans le code

Avec un MCP, tu exposes une liste de tools. Les bons clients proposent une allowlist ou une confirmation par outil, mais c'est une couche de configuration, extérieure au code appelé.

Avec un skill Python, le refus des actions destructives est dans la même codebase que l'usage : un test sur une liste de tools interdits, avec un message qui explique pourquoi et pointe vers l'alternative.

Une limite à assumer, parce qu'elle est structurelle : dès lors que l'agent dispose d'un outil terminal, le vrai périmètre de sécurité c'est le terminal, pas nos scripts. Un modèle qui veut supprimer un pod peut lancer kubectl directement. La blacklist applicative réduit les erreurs, elle ne contient pas un agent adversarial. Le vrai garde-fou est ailleurs : RBAC du service account, credentials en lecture seule, réseau restreint.

4. Portabilité : stdlib d'abord

Nos skills d'intégration API n'importent que urllib, json, ssl, time, argparse, sys et datetime. Aucune dépendance externe : pas de requirements.txt à faire évoluer, pas de désynchronisation dev/prod, une image d'agent qui n'a pas besoin d'un gestionnaire de paquets au runtime.

Une exception assumée : le skill d'automatisation navigateur embarque Playwright et Chromium. On ne réécrit pas un moteur de rendu en stdlib. La règle est donc « stdlib par défaut, dépendance lourde uniquement quand elle est le produit ».

5. Debug : le script en isolation

Un MCP qui plante, c'est du protocole stdio à débugger, des logs éparpillés, une trace qui traverse trois couches d'abstraction.

Un skill Python qui plante, c'est un docker exec avec la commande exacte, la sortie dans le terminal, une stack trace native, et la possibilité d'importer la classe dans un REPL pour jouer avec.

docker exec agent-container python3 \
  /path/to/skill/scripts/whatever.py <subcommand> --flag <value>

6. Évolution : 5 lignes pour ajouter un endpoint

Un endpoint ajoute un paramètre ? Sur un MCP, tu attends que l'upstream publie, tu bumps ta config, tu redéploies. Sur un skill maison : 5 lignes dans api_client.py, commit, propagé et testé en 2 minutes.

Les 8 règles qu'on a apprises à la dure

1. La description est du produit, pas de la doc technique

C'est le seul texte que le LLM voit avant de choisir un skill. Traite-la comme du copywriting :

  • 3 à 5 phrasings concrets tels que l'utilisateur les prononcerait, dans sa langue ;
  • les mots-clés exacts du domaine ;
  • ce qui n'entre pas dans le périmètre, explicitement.

« works with users » : le LLM ne choisit pas. « list users of a site, get user by email, filter by role admin/editor » : matching quasi immédiat.

2. Descriptions mutuellement exclusives entre siblings

Deux skills de la même catégorie ne doivent pas partager le même mot-clé porteur. Si skill-A dit « top scorers » et skill-B aussi, le LLM tire à pile ou face.

Avant de shipper une catégorie, on passe une matrice de conflit : lignes = tous les skills, colonnes = 5 à 10 phrasings réalistes. Chaque cellule doit avoir exactement un gagnant.

3. « NOT for X, see /other-skill » : obligatoire

Chaque skill spécialisé liste, dans sa description et dans son body, les cas adjacents avec le sibling correct. Le skill « cron health » dit : « NOT for application exceptions (see /error-tracker). NOT for raw logs (see /log-search). » Ces clauses fonctionnent comme des panneaux « route interdite ».

4. Petits skills plutôt qu'un monolithe

Cible : 4 à 10 skills spécialisés par catégorie, 80 à 150 lignes chacun.

L'alternative que beaucoup essaient d'abord, un seul gros skill qui contient tout, noie le LLM sous 3 000 lignes de doc dès qu'il le charge. Trop peu de skills : chacun devient trop large et ambigu au routage. Trop de skills : la matrice de conflit explose.

5. Confirmation explicite pour les writes

Aucune opération destructive lancée sans que l'utilisateur ait confirmé, dans le tour en cours, l'action exacte avec ses paramètres. La règle est écrite dans le SKILL.md, et le LLM la lit avant d'appeler.

À traiter comme une réduction du risque d'erreur, pas comme un contrôle d'accès : une instruction en langage naturel se contourne. Les vrais garde-fous restent les permissions du service account.

6. Blacklist des actions destructives dans le code

Pour tout skill qui expose une escape hatch générique (« appelle n'importe quel endpoint de l'API »), on maintient une blacklist en dur dans le script.

_DESTRUCTIVE_TOOLS = frozenset({
    "apply_resource",
    "patch_resource",
    "delete_node",
    "manage_gitops",
    # ...
})

def cmd_call(args):
    if args.tool in _DESTRUCTIVE_TOOLS:
        return refuse_with_hint(args.tool)

La discipline documentaire est la première ligne, le refus par le code la seconde.

7. Failure isolation dans les rapports agrégés

Nos rapports agrègent plusieurs sources. Règle : si une source tombe, les autres sections doivent quand même se rendre. Chaque appel passe par un wrapper qui capture l'exception et renvoie un marqueur d'erreur, que le rendu affiche inline. L'utilisateur voit ce qui a marché, ce qui a échoué, et pourquoi.

def _safe(func, *a, **kw):
    try:
        return func(*a, **kw)
    except ApiError as e:
        return {"__error__": str(e)}

data["issues"]  = _safe(client.issues)
data["metrics"] = _safe(client.top_resources, kind="pods")
data["events"]  = _safe(client.get_events)

# render() affiche _Radar tool failed: ..._ inline si __error__ est présent

8. Chain-to documenté, jamais codé

Un skill de rapport peut suggérer d'autres skills pour aller plus loin, mais il ne les appelle jamais depuis son code Python. La sortie contient une section « Chain-to for deep-dive » avec des commandes prêtes à l'emploi pour le tour suivant.

Pourquoi c'est important : l'orchestration appartient au LLM. Si un skill en appelle un autre en dur, on crée des dépendances cachées, on duplique la logique de routage, et on empêche les choix contextuels.

Ce que ça change concrètement

L'agent ne s'embrouille plus. Avant : « je charge skill-A pour vérifier », puis « skill-B au cas où », puis « en fait c'était skill-C ». Depuis qu'on tient la discipline sur les descriptions, c'est le bon skill du premier coup, à chaque coup.

Réponses plus rapides. Un skill chargé, c'est une centaine de lignes en contexte au lieu d'un manifeste géant. Moins de lecture pour choisir, moins d'allers-retours à vide. Sur nos questions ops courantes, on est passé de trois ou quatre tours de zigzag à un ou deux. C'est une mesure au chrono sur nos propres prompts, pas un benchmark.

Onboarding d'une capacité en une soirée. Un dossier, une description narrow, un script argparse de 100 lignes, une ligne dans la table de décision du router. Compter 2 heures pour une capacité simple, une journée pour une catégorie de 5 ou 6 skills.

Debug trivial. Un fix sur un script Python est effectif immédiatement. Un bug de routage : on ajuste la description du frontmatter, on ouvre une nouvelle conversation, réglé.

Le code est auditable. 100 lignes de Python stdlib qu'un ingénieur lit en 5 minutes.

Ce qu'on a construit avec ce pattern

Cinq catégories, une trentaine de skills :

  • Données métier via API tierces : router plus N skills par sous-domaine.
  • Ops internes : accès lecture seule à nos outils dev (repo Git, tracker d'erreurs, moteur de logs, plateforme BI).
  • Monitoring et health checks : crons applicatifs, trends d'erreurs HTTP, rapports de santé du cluster.
  • Automatisation navigateur : Playwright et Chromium pour les formulaires, redirects, screenshots, Core Web Vitals, crawl de liens.
  • Rendu de documents : PDF thémés, charts, classeurs Excel et CSV.

Point commun : router plus specialists, descriptions étroites, chain-to documenté.

Le gabarit

On maintient un « skill de méta-skill », utilisable depuis Claude Code, qui guide la création de toute nouvelle capacité : structure de catégorie, scaffolding du client HTTP partagé, rédaction du SKILL.md avec le bon frontmatter, génération de la CLI Python, propagation et smoke tests.

Il tient dans un seul fichier et il est copiable tel quel : il suffit de substituer les paths et préfixes.

fleox/hermes-skills-maker : meta-skill Hermes skill, usable from Claude Code, that guides the creation of any new capability: category structure, shared HTTP client scaffolding, writing the SKILL.md with the correct frontmatter, generating the Python CLI, propagation, and smoke tests.

Quelques règles qu'il encode, si vous voulez juste les idées :

  • Tout en anglais, frontmatter comme code, sauf les phrasings utilisateur cités entre guillemets, qui restent dans la langue des utilisateurs.
  • Un skill par sous-domaine de questions, jamais un par endpoint HTTP.
  • Matrice de conflit obligatoire avant de shipper.
  • Cap dur sur la taille du SKILL.md ; au-delà, le détail part dans un dossier references avec une consigne explicite de quand les charger.
  • Contenu utile uniquement : n'explique pas au LLM ce qu'est le HTTP ou un PDF. Le test : « est-ce que le LLM se tromperait sans cette ligne ? » Si non, on coupe.
  • Des défauts, pas des menus : « utilise pdfplumber » plutôt que « tu peux utiliser pdfplumber, PyMuPDF, pdf2image… ».
  • Section Gotchas = faits spécifiques à ton environnement, jamais de conseil générique.

Deux pièges qui nous ont coûté cher :

  • Ne jamais paginer sur un compteur post-filtre. Si tu filtres côté client, la condition d'arrêt doit porter sur la taille de la page brute, sinon une page entièrement filtrée simule une fin de données.
  • Attention aux conventions de codes de sortie. argparse sort en 2 sur une erreur d'usage : n'utilise pas 2 pour tes erreurs métier, tu ne pourras plus distinguer les deux dans tes scripts d'appel.

À retenir

  • Le pattern gagnant : router plus specialists, descriptions étroites, discipline sur les frontmatter. Ce n'est pas magique, c'est du copywriting.
  • La progressive disclosure change la donne. Seul le frontmatter est en contexte permanent, à condition que les skills restent petits et bien décrits.
  • Skills Python maison plutôt que MCP stdio tiers pour toute intégration qui doit être maîtrisée, auditable et évolutive à ton rythme. Les MCP restent bons pour du prototype, pour des outils publics qu'on ne veut pas maintenir, et pour les serveurs distants maintenus par l'éditeur.
  • La description du frontmatter est le facteur numéro 1 de fiabilité. 30 minutes à la ciseler par skill. C'est le seul texte que le LLM voit avant de choisir.
  • Le gain le plus notable, c'est la fin des hésitations. Un agent qui charge le bon outil du premier coup vaut mieux qu'un agent qui zigzague entre des skills mal découpés.

La discipline transfère quel que soit le runtime : Claude Agent SDK, OpenAI Assistants, LangGraph, ou maison.
